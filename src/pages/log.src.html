How airworthiness-mcp is tested before any code

The public repository freezes the question before Stage 0. The pass and fail rules are written down first, then fingerprinted, and only then would any code be allowed to start. That order is the decision: a result cannot be tuned against a rule that was written after the run.

{{claim:aw-prereg}} {{claim:aw-rules}}

The method note, dated 4 November 2026, splits the build into roles so that no single model both writes the work and judges it. Reviewers are never the builder. A reviewer score is advisory. The hard gates are specified to be run by code, and citations are specified to be checked by code. Isaac reviews and signs the merged fix list in that plan. After three review rounds without passing the gates, the plan says the work stops and he decides.

How TextBackCaller stops a send it should not make

A missed call is not, by itself, a reason to send a text. The service is specified to refuse the send when a guard fails, and to stop for a person when setup itself fails.

{{claim:tbc-no-repo}} {{claim:tbc-guards}} {{claim:tbc-controls}} {{claim:tbc-gate-alerts}} {{claim:tbc-gate-flags}} {{claim:tbc-gate-release}}

Read together, the account is: signed webhooks, a duplicate check, an opt-out, a usage cap, and a test run before a release. A second text to the same caller inside 24 hours does not go. A number that is not a UK mobile does not get a text. The owner's own call is skipped. If provisioning fails, or a trial is refused, the owner is told and a person chooses the next step. A new feature stays off until a separate approved change turns it on, and a kill switch can turn it off again.

The simulated pipeline walks five of those branches. It does not call Twilio, Stripe or Resend.

Source: the claims ledger on this site. The service code is not in a public repository, so these points stay marked as shipped or human-gate claims with self-reported evidence, except where a public page is linked from the ledger.
