airworthiness-mcp

Pre-registered study

This is a pre-registered study, not a working product. Nothing has been built or run. There is no live demo, no video, and no trial result. It is not a certification. The 16 of 16 detection line belongs to crs-ai-agents, not to this study.

Repository How the tests are set Earlier pilot it builds on

Problem

Before a person signs a release, the work pack has to support that signature. The planned tool reads one synthetic work package and lists what is open, overdue, missing or out of limits, with the source of every finding. It does not sign.

SpecifiedSpecified as a read-only checker of synthetic aircraft maintenance records. It is not specified to certify, release or determine airworthiness. A named human would decide.

What is specified

Five checks: open defects and deferrals, part life limits, tasks coming due, airworthiness directive status, and whether the work package is complete. Missing data is flagged and not guessed. The report is specified never to say an aircraft is released, ready, serviceable or airworthy. There is no tool in the design that can sign, approve or release.

SpecifiedThe design says a rules engine decides every finding. An optional local language model may only read free text, cannot remove or downgrade a rule finding, and is off by default.

The planned default is a command line program on the operator's own machine: rules only, no network, no API key, no model. An MCP server is specified for someone who already uses an MCP client on that same machine. An optional local IBM Granite model may read free text. Mistral is named as the second choice. That mode stays off until the operator switches it on. A further hosted-chat mode is described as an organisation's choice, not as something built.

Every aircraft, registration, part, defect and task in the plan is invented. The repository says the tool is not for real aircraft or real release decisions, and that it is not approved by any aviation authority.

Stack

Specified as Python, a deterministic rules engine, a hash-chained audit log, and an optional local model. Nothing in that stack has been run. The repository layout lists a data generator and 394 generated packages as part of the pre-registration materials. Those packages are test inputs for a trial that has not started. They are not a result.

How it will be tested

SpecifiedPass and fail criteria for 70 tests, T01 to T70, are written down and fingerprinted with SHA-256 before Stage 0. They have not been run.

The method note says acceptance is a code gate, not a review score, and that a model cannot review code it or its own family wrote. The detail is in the engineering log.

What I owned

The README says I am building it myself, using AI models as build and review tools under a method I designed, and the same README says nothing has been built or run. Every design decision, threshold and acceptance call is described as mine. The ownership on record is the method and the written plan, not a finished program.

The README states more than 15 years in aircraft maintenance. This site uses that as the method behind the design. It does not call me a licensed engineer, a Part-66 licence holder, or an aircraft mechanic. The tool's own required line, once a report exists, is specified as "AI assists, a certifying human decides." No such report exists yet. The three human reviewers named in the plan, including a B1 certifying engineer, are not appointed.

Evidence

There is no impact figure. A pass rate is not shown because a pass rate would be invented. The plan names 70 tests, and the repository layout lists 394 generated packages as inputs for a trial that has not started. Neither figure is a result.

Source: DealEnvoy/airworthiness-mcp, including the README and docs/methods.md, read 15 November 2026.
